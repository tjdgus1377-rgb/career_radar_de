# Career Radar — 실행 계획

- 갱신일: 2026-11-04
- 상태: 제안된 MVP 순서. 소스 승인과 환경 준비 이후 각 단계 착수
- 관련 문서: [요구사항](requirements.md), [데이터 소스](data-sources.md)

`plan.md`는 제품 기능이 아니라 프로젝트 작업 순서와 완료 조건을 추적하는 문서입니다. 기능 요구사항은 `requirements.md`, 단계별 구현 계획은 이 문서에서 관리합니다.

## MVP 결과

데이터 엔지니어 직무를 대상으로 최근 기간 공고에서 (1) 많이 언급된 기술 순위, (2) 같은 공고의 같은 요구 항목에서 명확히 함께 나온 기술 조합, (3) 개인 보유 기술을 입력받아 다음 학습 항목을 보여주는 서비스를 배포합니다.

첫 추출 버전은 **기술 사전 문자열 매칭**으로 구현합니다. 자격요건/우대사항 영역과 근거 문장을 함께 저장합니다. 경력·도메인·커뮤니케이션 표현은 기술 순위에 섞지 않습니다. 모호한 대안 나열은 조합으로 만들지 않습니다. LLM 기반 추출은 MVP에 포함하지 않습니다.

## 단계별 계획

### 0. 저장소와 범위 확인

- [ ] 현재 파일·패키지 구조와 개발 환경 확인
- [ ] 데이터 엔지니어 직무 및 첫 분석 기간을 MVP 기준으로 기록
- [ ] 비밀값·원본 공고가 저장소에 들어가지 않도록 확인

**완료:** 실행할 개발 환경과 MVP 범위가 README·요구사항과 일치합니다.

### 1. 데이터 소스 승인과 샘플 확보

- [ ] 최소 한 출처의 공식 접근 방식과 저장·분석·표시 조건 확인
- [ ] 실제 공고 수십 건 확보: ID, 제목, 날짜, 자격요건, 우대사항, URL 포함
- [ ] 본문에서 기술 사전 매칭이 가능한지 수작업 표본 검토
- [ ] 수집량·페이지네이션·호출 한도·증분 날짜 필터 기록

**완료:** 사용할 수 있는 출처가 하나 이상 있고, 기술 분석에 필요한 텍스트를 사용할 수 있습니다. 접근이나 이용 조건이 통과되지 않으면 다른 소스를 검토하고 임의 크롤링을 시작하지 않습니다.

### 2. 원본 저장과 최소 수집기

- [ ] Python 출처 어댑터 작성
- [ ] API 응답 또는 허용된 페이지 원본을 로컬 비공개 저장소에 보관
- [ ] `(source, external_id)`로 중복되지 않게 적재
- [ ] 등록일·수정일·최초/최종 수집시각 저장
- [ ] 오류 응답·누락 필드·수집 건수를 기록

**완료:** 샘플을 재수집해도 공고가 중복되지 않고, 수집 결과를 원본으로부터 다시 처리할 수 있습니다.

### 3. 정제와 기술 사전 추출

- [ ] 공고를 직무·경력·자격요건·우대사항 단위로 정리
- [ ] 첫 기술 사전 작성: 예) `PostgreSQL` 별칭 `Postgres`, `GCP` 별칭 `Google Cloud`
- [ ] 문장 안에서 사전 기술명을 찾아 표준 기술명으로 저장
- [ ] 항목 유형, 근거 문장, 공고 버전, 매칭 규칙 버전 저장
- [ ] 한 공고의 동일 기술 중복을 제거
- [ ] 기술이 아닌 경력연수·도메인·협업 역량은 별도 필드로 두거나 1차 분석에서 제외
- [ ] 추출 결과를 표본과 대조하고 사전·별칭을 보완

**완료:** 공고별 기술 목록과 각 기술을 찾은 원문 문장·필수/우대 영역을 설명할 수 있습니다.

### 4. 빈도와 기술 조합 집계

- [ ] 등록일 기준 최근 N개월의 유효 공고를 선택
- [ ] 기술별 고유 공고 수와 본문 분석 가능 공고 대비 비율 계산
- [ ] 필수/자격요건과 우대사항 통계를 구분
- [ ] 같은 공고의 같은 항목에서 명확히 함께 요구된 기술만 조합으로 계산
- [ ] `A 또는 B`, `A/B`, `A, B 등` 같은 대안 목록은 조합으로 만들지 않음
- [ ] 표본 수·기간·출처·본문 확보 수를 함께 반환

**완료:** SQL로 기술 순위와 조합 표를 재현할 수 있고 분모가 분명합니다.

### 5. 개인별 학습 우선순위

- [ ] 사용자가 현재 보유한 기술 선택
- [ ] 준비 항목별 필수/우대 언급 빈도와 근거 표시
- [ ] 이미 보유한 항목은 완료 상태로 표시
- [ ] 소규모의 사람이 검토한 선행관계 사전 작성 (예: SQL 기초 → 데이터 모델링/변환 실습)
- [ ] 빈도와 선행관계를 설명 가능한 규칙으로 결합
- [ ] 신입 사용자는 경력 3년 이상 등 조건이 맞지 않는 공고를 구분해 표시

**완료:** 추천 항목마다 “왜 지금 준비할지”를 빈도·요구 구분·선행관계로 설명합니다. 추천을 취업 성공 확률로 표현하지 않습니다.

### 6. Airflow 자동화와 품질 관리

- [ ] 수집 → 저장 → 추출 → 집계 작업을 Airflow DAG로 연결
- [ ] 일 1회 등 실행 주기는 샘플 수집과 호출 한도를 확인해 결정
- [ ] 실패 재시도, 체크포인트, 재실행 안전성 구현
- [ ] 호출 수·신규/수정 건수·본문 확보율·실패 건수·마지막 성공시각 기록
- [ ] 실패한 새 결과가 직전 정상 집계를 덮어쓰지 않게 처리

**완료:** Airflow에서 정기 실행을 확인하고 일부 작업 실패 후 안전하게 복구할 수 있습니다.

### 7. API와 웹 화면

- [ ] FastAPI에서 기간·경력·보유 기술 조건으로 결과 제공
- [ ] Svelte 화면에서 기술 순위·조합·학습 우선순위 표시
- [ ] 표본 수·집계 기간·출처·마지막 갱신시각·근거 공고 표시
- [ ] 표본이 없거나 부족하면 그 사실을 표시

**완료:** 취업 준비자가 입력을 바꾸어 결과를 확인하고 추천 근거까지 볼 수 있습니다.

### 8. 배포와 End-to-End 완료

- [ ] Docker Compose 등으로 애플리케이션과 데이터 저장 환경 재현
- [ ] 배포 환경의 키·DB 접속정보 비밀 관리
- [ ] 수집→분석→API→화면 갱신의 운영 실행 확인
- [ ] 실행·재처리·장애 확인 절차와 데이터 이용 조건 문서화

**완료:** 새 공고가 허용된 방식으로 수집되고 자동 집계 후 서비스 화면에 반영됩니다.

## 초기 추출 예시

공고 문장: `Python과 SQL로 대용량 데이터를 처리할 수 있는 분`

```text
job_id: 123
section: qualification
skills: [Python, SQL]
co_occurrence: 명확한 동일 항목에서 함께 요구
```

공고 문장: `Airflow, Dagster 등 오케스트레이터 운영 경험`

```text
job_id: 123
section: preferred
skills: [Airflow, Dagster]
co_occurrence: 만들지 않음 (대안 목록일 수 있음)
```

## 계획 변경 원칙

각 단계에서 실제 API 응답·사용 정책·공고 표본이 설계와 다르면 `data-sources.md`와 `requirements.md`를 먼저 갱신하고 이후 단계 범위를 조정합니다. 완료한 단계의 증거(샘플 위치, 실행 방법, 관찰 결과)를 이 문서에 짧게 기록합니다.
